# Conclusion

Process mining research produces new methods faster than the tools people actually analyse processes with can absorb them. The commercial suites are analytically broad, operationally mature and closed: extension happens inside a vendor-governed application model, so a method published this year cannot be run in them this year. The open toolkits are genuinely extensible, and are single-user, stateless and interface-less, because multi-user operation was never in their scope. A researcher with a published method has no path to a place where a non-developer can use it.

The approach taken here was to build the missing layer rather than another algorithm. Mate is a locally hosted, multi-user process mining platform whose defining property is that **analysis methods are contributed as self-contained modules the platform discovers, isolates and mounts, without modification to the platform itself**. Two application services and a bundled identity provider run on one host with embedded storage, no broker and no cloud dependency. A manifest declares a module's registration, requirements and dependencies; a class instantiated once per process carries route, event and job handlers; a Protocol-typed context supplies data access, a scoped result cache, configuration, progress reporting and inter-module communication. Each module resolves its own dependencies into its own environment, and a module needing a different interpreter, or a different language entirely, runs behind a documented worker protocol instead.

The guiding question of §1.2 asked whether such a platform could be built without its own analytical functionality receiving any privilege a third-party extension does not also receive. The answer is **yes**, and the evidence is structural rather than rhetorical: all seventeen bundled modules, including the three supplying the platform's baseline discovery, performance and object-centric capabilities, are authored through the same public SDK, and the platform's source contains no module-specific branch, registry entry or import. The constraint was self-imposed precisely because a contract its authors need not use is one whose inadequacies never surface.

Three claims are supported by the work reported here.

**The module contract carries first-party and third-party, Python and non-Python extensions alike.** Six integrations produced 2,298 lines of platform change in total, all in one integration and all building the general JVM runtime rather than accommodating a particular module; the other five changed nothing. A research repository of command-line scripts, a Java algorithm shipped as a jar with no Python in the module folder at all, a module requiring a graph database beside the platform, and a module calling an external language model were all absorbed by the same mechanism.

**Isolation holds across every layer.** One identity claim keys database rows, on-disk directories, job records and live event envelopes, with a single deliberate exception, read-only dashboard sharing, confined to one auditable module of predicates.

**Local operation is achievable without an operations team.** One idempotent script takes a bare virtual machine to an authenticated, TLS-terminated deployment behind the institutional proxy, and the same repository runs unchanged on a laptop.

What remains unproven should be stated with equal directness. **The extensibility claim rests on six integrations by the people who wrote the contract.** They knew it without reading it, they could change it when it did not fit and did so five times, and the modules were chosen partly because they would stress the mechanism. No external author has been observed working through Chapter 8 under conditions that would let anyone measure what it costs, so the authoring experience, as opposed to the contract, is not measured at all. Nor is the isolation claim a security claim: a module runs with the platform's privileges, and installing one is equivalent to running code on the server. Analytical breadth is not close to the commercial suites, there is no connector ecosystem, and the single-host design becomes binding at a predictable and not very high threshold of concurrent heavy analyses.

For the institutional context in which the system now runs, the significance is concrete. Event logs that could not previously be analysed in a hosted tool, because the data may not leave the university, can be analysed here. A cohort of students can be given accounts on one installation instead of twenty desktop environments, and the artefacts they produce outlive any licence. A master's thesis on complexity metrics and a published drift-detection method have both become things a person can click on. And the next method to arrive costs its author a manifest, a class and an adapter, rather than a product.

That last property is the one worth generalising. Nothing in the contract, the declared-event ordering model or the readiness gate mentions event logs; they would transfer to any analytical platform whose workload is an artefact in and an artefact out over a large shared dataset. The specific contribution of this project is not a process mining technique. It is the demonstration that the distance between a published method and a usable one can be made short, and that making it short does not require giving up either local operation or multi-user isolation.
