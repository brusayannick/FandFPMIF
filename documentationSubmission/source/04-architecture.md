# Platform Architecture

## Architectural Overview

Mate is two application services plus a bundled identity provider. The `api` service is a FastAPI application holding all process mining logic, the HTTP surface, the job runtime and the module system. The `web` service is a Next.js application rendering the user interface. Identity comes from a bundled Keycloak instance, the only component with a database of its own: a small PostgreSQL container for accounts, sessions and realm configuration. Everything else the platform persists lives in one bind-mounted directory on the host, a SQLite file for metadata and Parquet files for event data. There is no broker, no cache server, and no runtime dependency on any service outside the host.

The service cut easiest to misread is that **the browser talks to the `api` service directly** rather than routing every call through the Next.js server. Using Next.js as a backend-for-frontend would have inserted a second network hop in front of every request, required duplicating authorisation logic in TypeScript, and made streaming job progress a matter of proxying through a Node process. Instead the API URL is inlined into the client bundle at build time, the browser attaches its bearer token directly, and CORS permits exactly the web origin. Server components still reach the API through an internal URL with the cookie-backed token, but that path serves initial render, not interaction. In production both origins collapse onto one (§7.4), at which point CORS becomes moot.

Four invariants are established here and respected throughout. **No component may require an external service at runtime.** **Every user-scoped artefact carries the authenticated identity**, at rest and in flight (§4.5). **Anything that can outlast a request is a job**, never a long-held HTTP connection (§4.7). And **the platform's own analytical functionality has no privilege a module lacks**, which makes the module contract load-bearing rather than decorative (Chapter 5).

## Infrastructure and Deployment Modes

The stack is described once in `docker-compose.yml` and specialised by overlays (Docker Inc., 2024). This is the most frequently misunderstood point about the deployment: **the four running modes are layered configurations of one composition, not four tools.**

The base composition defines four services, `keycloak-db`, `keycloak`, `api` and `web`, builds production images and publishes ports 3000, 8000 and 8080. The **development overlay** mounts the source tree and replaces the entrypoints with `uvicorn --reload` and `next dev`. The **production overlay** adds a Caddy `proxy` terminating TLS on 443 and routing by path, repoints the public URLs at a single origin, and withdraws the published ports (§7.4). Outside Docker, `make dev` runs both dev servers on the host: the fastest inner loop, and the one module authors are directed to (§8.1). §7.3 gives the decision rule. One further service exists but is off by default: a Neo4j container declared under the `graph` compose profile and started only when a module needs a graph database beside the platform (§5.5).

## Authentication, Authorisation, and Administration

Login is mandatory; there is no anonymous mode and no path reaching data without an authenticated identity.

The identity chain has four links. The browser is redirected to the bundled **Keycloak** realm, which either presents its own form or delegates to the university identity provider. Keycloak returns an authorisation code to the web application, where **Auth.js v5** exchanges it and issues a session (Auth.js, 2024). Sessions are **JWT-only**, with no database adapter and no session table on the application side, and token rotation in the `jwt` callback. The browser then calls the API with a bearer token, which the API validates with **PyJWT against the realm's published JWKS endpoint**, caching the key set so validation costs no network round trip. The `sub` claim is the user identity for everything that follows, and the first time one is seen the API upserts a row for it.

Authorisation uses exactly one primitive, the realm role `admin`: no per-resource permissions, no groups mapped to capabilities, no policy language. This is a deliberate simplification for a system in which almost every authorisation question is answered by ownership rather than role, which §4.5 enforces structurally. The administrative surface covers system and usage state, live control of worker concurrency, module policy (an administrator can pin a module as globally enabled or locked), user and team administration, and a **consistent metadata export**: one SQLite file holding a transactionally consistent snapshot of the whole metadata database, gated on the `admin` role. Its governance implication is stated rather than buried: **the export contains every user's accounts, usage data, process metadata and settings**, so the download is itself sensitive.

Usage capture deserves the same directness. Interaction events are recorded locally, and the data model follows the reference data model for process-related user interaction logs of Abb and Rehse (2024): events are stored with OCEL-shaped objects (UI element, UI group, application, system, user, task) and the relations between them, so the platform's own usage is itself analysable as an object-centric event log. Nothing is transmitted off the host. The default policy, however, is `force`, which enables capture for every user and hides both the onboarding privacy step and the privacy settings tab; the operator can select opt-out or opt-in instead. §7.6 treats this as a governance decision rather than a configuration detail.

## Tenant Isolation as a Cross-Cutting Invariant

Isolation is not a feature with an owner; it is a property every layer must independently maintain. Stated in the form a contributor must keep true:

> **Invariant.** Every artefact belonging to a user is keyed by that user's Keycloak `sub` claim, at rest and in flight. A component producing a user-scoped artefact without that key is broken, whether or not anything currently reads it.

Four places honour it. **Database rows**: every user-scoped table carries a `user_id` column referencing the users table with cascade deletion, and access goes through ownership helpers rather than ad-hoc filters, so "did this query forget the tenant predicate" is a question about a handful of functions rather than every route. **On-disk artefacts**: Parquet data and module result caches live under `data/users/{user_id}/`, so the path encodes the boundary. **Job records**: a job carries its owner, and pause and resume operate per user. **Live events**: every user-scoped bus envelope carries `user_id` as a reserved key, and the SSE fan-out filters on it server-side before writing to a connection.

The last has the sharpest failure mode. The bus has no notion of tenancy of its own; isolation is enforced at fan-out by comparing the envelope's `user_id` with the connected user's. An event emitted **without** a `user_id` is therefore not filtered and reaches every connected session. That is correct for a genuinely global notice and a data leak for anything else. The rule is absolute: **a user-scoped event omitting `user_id` leaks to all users**, and the omission is silent, since nothing crashes and nothing warns. §8.11 lists it among the failure modes an author must know.

One exception is deliberate and confined. A dashboard may be shared, granting named recipients **read** access to that dashboard and, transitively, to the underlying log's data as its cards render it. Every predicate that widens access lives in a single module, so the surface capable of crossing an account boundary is small enough to audit in one sitting. Recipients cannot mutate the dashboard or reach the log by any other route.

## Data Management: Ingest, Columnar Storage, and Offloading

An upload is staged to disk, its format detected, and an import job enqueued; the request returns a log identifier and a job identifier immediately. Parsing dispatches on format: XES and its gzipped variant through a streaming XML reader, CSV through a column-mapping step, generic XML through a mapping-based path, and OCEL 2.0 through a separate object-centric path. The canonical form is written once per log:

```
data/users/{user_id}/event_logs/{log_id}/
  meta.json          source format, ingest statistics, detected schema, mapping
  events.parquet     flat event table, sorted by (case_id, timestamp)
  cases.parquet      cached case-level aggregates
  original.{ext}     the untouched upload, for audit and re-export
  ocel/              object-centric imports only: events, objects, relations, o2o
```

The rationale is §2.1's structural assumption. XES on disk is XML, so answering "how many events per activity" means parsing hundreds of megabytes of markup for one aggregation. Normalising once into a columnar format makes that aggregation essentially free, shrinks the data by roughly an order of magnitude, and is read natively by every library a module might want. Keeping the original beside the derived form preserves auditability and makes re-import possible.

Analytical queries run against DuckDB reading those Parquet files while metadata stays relational in SQLite, and DuckDB can attach the SQLite database so a query can join the two in one statement. Because a DuckDB connection is single-threaded, connections are pooled per worker thread through context variables. Per-query thread and memory limits are configurable, so one large query or one dashboard full of cards cannot claim every core on a shared machine.

Beyond a certain volume the VM's disk becomes the binding constraint, so the platform supports an **object-storage backend**. The first implementation was a write-through mirror, and it did not work, for reasons worth reporting. A mirror writes locally then uploads, and on a read miss pulls the whole directory back; the local copy was never evicted, so enabling object storage added a second copy and an upload cost without shrinking the VM. Worse, the artefacts actually consuming disk bypassed the mirror entirely: the metadata database, each module's virtual environment, the cached Python runtimes and uploaded module packages. Hydration was whole-tree and per-process, so a cold read of a ten-gigabyte log pulled all ten gigabytes before DuckDB touched a row, once per worker.

The redesign inverts the relationship. **Object storage is authoritative; local disk is an LRU cache** bounded by an explicit byte budget, with age-guarded eviction and a dry-run mode for a soak period before deletes are enabled. The bypass holes were closed, migration between backends moves existing data rather than stranding it, the previously declared per-user quota is enforced, and hydration became partial and shared. With a budget configured, the local footprint is bounded by the active working set plus module runtime artefacts rather than by total data ever imported. Two seams are deliberately left open for multi-node operation and named again in §11.4: the cache is per-node with no cross-node coordination, and the metadata database remains a single-writer store whose loss would orphan every object in the bucket.

## Backend: API Surface, Job Runtime, and Event Bus

**The HTTP surface** lives under `/api/v1/`, organised by resource: event logs and their data, folders, datasets, jobs, modules, dashboards, sharing, teams, watched folders, preferences, onboarding, API tokens, the assistant, usage, and an administrative group. Module routes mount under `/api/v1/modules/{module_id}/...`, so a module's surface is namespaced by construction and cannot collide with the platform's or another module's. OpenAPI is generated rather than written, so no hand-written API types exist in the repository.

**The job runtime.** A producer inserts a row into the SQLite jobs table, assigns a time-ordered UUID v7 and pushes a marker onto an in-process `asyncio.Queue`; a pool of asyncio workers consumes it. Concurrency defaults to two and is changeable live by an administrator, resizing the pool without interrupting running work. Cancellation is cooperative through a per-job event handlers check, and retry re-enqueues the same payload under a fresh identifier so the failed attempt stays in the record. Because job state is in SQLite rather than memory, a restart does not lose the queue: on boot the runtime reconciles what it finds. There is no Redis, no Celery and no broker. For CPU-bound work a process pool is available through the context, with a per-job execution timeout that can kill a runaway offload rather than merely marking a database row.

**The event bus** distributes state changes in-process. Publishers emit an envelope of topic, payload and timestamp; subscribers register topic patterns and are each fed through their own bounded queue. The queue policy is the decision worth explaining. Each queue holds a fixed number of envelopes, and when full **the oldest is dropped** rather than the publisher blocking. This is correct given what the bus carries: a `job.progress` tick is one sample of a continuously updating quantity, and losing it costs a slightly staler bar until the next tick, whereas letting one slow browser connection stall the import producing the ticks is far worse. A terminal event such as `job.completed` is not expendable in the same way, and the bus does not distinguish the two, so that property is achieved differently: terminal state is persisted to the jobs table before it is published, and the frontend reconciles against that table on reconnect. **The bus is a low-latency accelerator over authoritative database state, never the source of truth.**

Both live streams the browser consumes are bus subscribers: the session-wide, topic-filtered `GET /api/v1/events`, and the per-job `GET /api/v1/jobs/{job_id}/stream`. Both are Server-Sent Events, for reasons in §4.10.

## Progress Reporting and Readiness Semantics

A freshly imported log is not immediately useful, because several modules precompute on import and opening the log before they finish shows a page of empty cards. The platform therefore holds a log in `processing` until the analyses it waits for are done, and the semantics of that gate are the subtlest part of the runtime.

A log moves through `importing` while its source is parsed, then `processing` while modules precompute, then `ready`, or `failed` if the import itself errored. The set of modules that must finish, the **expected set**, is computed once at import time and frozen; computing it lazily would introduce a race in which the coordinator observes zero subscribers before any has registered and flips the log to `ready` immediately. The expected set is not simply the modules subscribing to the import event. It is the **transitive precompute closure**: starting from the job-backed subscribers to `log.imported` or `ocel.imported` that the importing user actually has installed, the loader walks the graph of declared `provides` and `consumes` topics, pulling in every module subscribing to a topic another expected module emits. Ordering is therefore expressed as an **event subscription, not a priority number**: a module that must run after discovery subscribes to `discovery.completed`, which the platform emits automatically when a precompute job succeeds. §5.6 explains why this is the better design.

Three properties follow. Because the closure is built from the actual subscription graph, a `consumes` entry naming a topic no loaded module emits is never reached, so a stale declaration degrades to a no-op rather than a stuck log. Because a failed or cancelled module emits no completion event, its dependants are **cascade-skipped** rather than stranded. And because the gate releases on any terminal status, a module that crashes delays a log by the duration of its own failure and no longer. Completion is derived from the job rows, linked to the import job by a parent reference, rather than from an in-memory counter, so an API restart mid-precompute recovers by re-deriving state from the database. The import job's payload carries the computed plan, which the interface renders as a checklist of what is waiting, finished and skipped.

Progress reporting inside a job is **optional and never enforced**. A handler may report a fraction, an absolute current-and-total pair which additionally enables an estimate of time remaining, or a plain running counter for work of unknown scope. A silent job is not an error: it degrades to an indeterminate bar, and after about three minutes without a tick the interface adds a stall hint. Making progress a runtime requirement was rejected because the enforcement would have to be a timeout, and a timeout killing a legitimately slow computation is a worse failure than a bar that does not move.

## Frontend: Structure, State, and Interaction Model

The application is organised by route group: authentication for the login flow, and a platform group for everything behind the session. Server components fetch through a server-side wrapper reading the cookie-backed token, serving the initial render; everything interactive goes through the browser wrapper, which attaches the bearer token and is consumed by TanStack Query hooks. The division between the two state systems is deliberate: **anything from the server lives in the query cache, and only genuinely local interface state lives in Zustand**. Preferences that look local, theme, density, visualisation settings, are held in Zustand for instant reads but bridged to per-user server state, so they follow the account across browsers instead of bleeding between accounts through shared browser storage.

Three interaction conventions follow from the product principles. **Optimistic mutation with snapshot rollback for edits**: a mutation modifying an existing resource cancels in-flight queries, snapshots the cache and writes the expected next state, restores the snapshot on error, and invalidates on settle so the server reconciles; creation and duplication use plain invalidation, because there is no prior row to roll back to. **Skeletons rather than blocking spinners** for above-the-fold content. **Motion as state feedback only**, short, never decorative, honouring reduced-motion preferences.

Module-contributed panels are the one part of the frontend not built by the Next.js build. A separate script bundles each module's declared panel and widgets with esbuild into the module's own output directory, once at container start in production and in watch mode in development. Every shared dependency, React itself, the query client, the component primitives, the charting and graph libraries, is marked external and resolved at run time from a shared runtime object the host installs lazily. That is what lets a panel use the host's React instance, so hooks and context work across the boundary and a panel inherits the host's theme. The cost is a constraint on authors: a panel may import only from an explicit allow-list of platform paths, held in a single file read by both the bundler and the runtime installer, with a parity test asserting the two never diverge. §5.7 develops the reasoning and §8.7 states the symptom when it is ignored.

## Error Handling and Operational Robustness


The mechanisms here were not planned. Each responds to a defect observed in operation, and they are collected together because scattering them would hide the pattern. Appendix E is the full record.

**The transport the proxy chain would not carry.** Live updates were originally WebSockets. They worked locally and failed silently in production, because the university's edge proxy forwards HTTP but does not carry WebSocket upgrades: the handshake arrived at the API as a plain `GET` with the upgrade headers stripped and returned 404. Nothing crashed; job progress simply never updated, and only in production. Both live streams were migrated to **Server-Sent Events over `fetch`**, which ride exactly the path the assistant's token streaming already used successfully. Two secondary benefits followed: because `fetch` can set headers, authentication moved from a query-string token to an `Authorization` header, so tokens stopped appearing in access logs; and because SSE is HTTP, a 401 is unambiguous and means "sign in again" rather than triggering an endless reconnect loop. Both streams reconnect with exponential backoff capped at eight seconds. The client file is still named `ws.ts`, because that path is a published module-SDK import alias and renaming it would break third-party panels.

**Worker supervision.** A bridged module runs in a separate process, and separate processes die. The host supervises its worker and respawns it with exponential backoff up to a bounded number of attempts, rather than letting one module's crash disable it until the next restart. The reverse hazard is a worker whose parent has died surviving as an orphan holding a socket and an environment, so the protocol requires every worker to implement a parent-death guard. Both behaviours have regression tests.

**A message-size limit that killed workers.** The bridge frames messages as newline-delimited JSON read through asyncio's stream reader, whose default line limit is 64 KiB. Handler return values, cache writes and result sets routinely exceed that, and a single oversized line raised an internal buffer error that tore down the connection and took the worker with it. The limit is now far beyond any plausible metadata payload and, more importantly, bulk data no longer travels the socket: DataFrames cross as a Parquet file on the shared filesystem.

**Contained failures.** Dependency resolution can fail on a bad specifier, an unreachable index or a package with no wheel; the failure is reported with the resolver's own error text, the module is marked failed to load, and the rest of the platform starts normally. And if a live stream drops, the interface neither freezes nor silently lies: jobs reconcile against the jobs table on reconnect, and a running job silent for about three minutes is annotated as such rather than left animating. The intent throughout is that the failure of a convenience layer degrades the experience without corrupting the state.

## Machine Access: MCP Server and Integrated Assistant

Two non-graphical access paths exist, both defined primarily by where their data boundary sits.

**The MCP server** exposes the platform to external AI clients over the Model Context Protocol. It is off by default. Eight toolsets cover metadata, processes, analysis, dashboards, jobs, watched folders, account settings and administration, with the administrative set excluded unless explicitly listed. Three properties define its posture. **The caller's identity is never a tool argument**: it is resolved from the authenticated principal on the connection, so a token can only act as its owner and §4.5's invariant holds by construction. There is a **data wall**: raw event rows are never returned, only aggregates and curated module outputs, so a client can ask what the process looks like but cannot exfiltrate the log row by row. And the server is scope-gated, rate-limited with a burst allowance, concurrency-capped per user and globally, and can be placed in a read-only mode that either unregisters write tools at boot or makes them refuse at run time. Authentication is by personal access token or OAuth 2.1 through the same Keycloak realm, with browser-based clients additionally guarded against DNS rebinding by an origin check.

**The integrated assistant** ("Mate AI") is a chat panel inside the application. Rather than coupling the platform to a model vendor, it targets any OpenAI-compatible endpoint: the user supplies base URL, API key and model name and may customise the system prompt. Those credentials live in the local metadata database as a per-user setting and are transmitted nowhere except to the endpoint the user configured. The assistant can reference the active log, recent job outcomes and enabled modules, and can carry out platform actions through the same guarded surface the MCP tools use.
