# Platform Architecture

## Architectural Overview

Mate is two application services and a bundled identity provider. The `api` service is a FastAPI application holding all process mining logic, the HTTP surface, the job runtime and the module system. The `web` service is a Next.js application that renders the user interface. Identity is supplied by a bundled Keycloak instance, which is the only component with a database of its own, a small PostgreSQL container that stores accounts, sessions and realm configuration. Everything else the platform persists lives in one bind-mounted directory on the host: a SQLite file for metadata and Parquet files for event data. There is no message broker, no cache server, no search index, and no runtime dependency on any service outside the host.

The one service cut that is easy to misread is that **the browser talks to the `api` service directly** rather than routing every call through the Next.js server. Next.js is capable of acting as a backend-for-frontend, and the default instinct is to use it that way. Doing so would have inserted a second network hop and a second serialisation boundary in front of every request, would have required duplicating the authorisation logic in TypeScript, and would have made streaming job progress to the browser a matter of proxying a stream through a Node process. Instead, `NEXT_PUBLIC_API_URL` is inlined into the client bundle at build time, the browser attaches its bearer token directly, and CORS is configured to permit exactly the web origin. Server components still reach the API through an internal URL using the cookie-backed token, which is what `apiServer()` does, but that path serves initial render, not interaction. In the production deployment both origins collapse onto one (§7.4), at which point CORS becomes moot and the arrangement pays off a second time.

Four invariants are established here and are respected by every subsequent section. First, **no component may require an external service at runtime**; anything that would need one is either embedded or optional. Second, **every user-scoped artefact carries the authenticated identity**, at rest and in flight (§4.5). Third, **anything that can take longer than a request is a job**, never a long-held HTTP connection (§4.7). Fourth, **the platform's own analytical functionality has no privilege a module lacks**, which means the module contract is load-bearing rather than decorative (Chapter 5).

## Technology Stack and Its Rationale

Every choice below was made against one recurring criterion, stated as design goal G1 in §3.5: the component must run embedded on a single host, without operational staff.

**Python 3.12 and FastAPI.** Python is the de facto language of the process mining ecosystem, which makes PM4Py and the reference implementations published with research papers directly usable rather than something to reimplement (Berti et al., 2023; Python Software Foundation, 2025). FastAPI derives its interface from standard type annotations and emits an OpenAPI description of the whole API as a by-product, which is what makes end-to-end type safety cheap (Ramirez, 2024). It is asynchronous by default, which shapes the whole backend: a request enqueues work and returns immediately rather than holding a connection open. Incoming and outgoing data are validated with Pydantic v2, whose models feed directly into that OpenAPI description (Pydantic, 2024). The alternative considered was Django with Celery, which was rejected because Celery requires a broker and therefore a third container, violating G1 for a benefit the workload does not need.

The interpreter version is **pinned to 3.12** in the repository's `.python-version`, so that development and the Docker image agree. This is worth flagging early because it later becomes a hard constraint: modules that run inside the platform process are compiled against this interpreter's ABI and cannot deviate from it (§5.4).

**uv, ruff and pyright.** Dependencies and virtual environments are managed by `uv`, a fast resolver and installer that lets every developer reproduce the same environment from one specification (Astral, 2025). Its speed is not a convenience here but an architectural enabler: the module system creates a separate virtual environment per module at startup (§5.3), which would be untenable with a slower installer. Code quality is enforced by `ruff` for linting and formatting and `pyright` in strict mode for static typing (Astral, 2024; Microsoft, 2024).

**SQLite for metadata.** Application state, process log metadata, jobs, module configuration, dashboards, teams and usage events, is transactional, small and row-oriented. SQLite provides full ACID guarantees with zero configuration and no second container (SQLite, 2024). It runs in WAL mode through `aiosqlite`, and schema changes are versioned by Alembic migrations that are applied automatically on boot. PostgreSQL was the alternative and was rejected for the application store on G1 grounds; it is present in the stack only because Keycloak requires it, and that database is deliberately kept separate and never joined against.

**DuckDB over Parquet for event logs.** Event data has the opposite profile: large, immutable, and read overwhelmingly by aggregation over few columns. Parquet is columnar and compressed, typically five to twenty times smaller on disk than the equivalent XES, and is read natively by pandas, polars and PM4Py (Apache Software Foundation, 2024). DuckDB queries those files in-process with no ETL step, giving sub-second aggregations over millions of events (Raasveldt & Mühleisen, 2019). Storing events in SQLite instead was measured to be the wrong shape by an order of magnitude for the group-by workload that dominates; PostgreSQL with a columnar extension would have matched the analytics but reintroduced the operational burden. §4.6 develops the consequences of this split.

**Next.js 15 with the App Router and React.** The frontend is a Next.js application using React Server Components where they help, so that parts of the interface render on the server and stream to the client while the JavaScript bundle stays small (Meta Open Source, 2024; Vercel, 2024). It is written in TypeScript in strict mode, applying the same preference for compile-time error detection as the backend (Bierman et al., 2014). The visual layer combines Tailwind CSS with shadcn/ui components, which are copied into the project rather than imported and can therefore be adapted freely (shadcn, 2024; Tailwind Labs, 2024). Server state is managed by TanStack Query and purely local interface state by Zustand (Poimandres, 2024; TanStack, 2024). Charts are rendered with Recharts and, for the more complex interactive ones, ECharts (Li et al., 2018; Recharts Group, 2024); node-and-edge diagrams such as directly-follows graphs, Petri nets and process trees are drawn with React Flow (xyflow, 2024), and BPMN with `bpmn-js`.

**Type synchronisation.** TypeScript types are generated from the backend's OpenAPI description by `openapi-typescript` and validated at runtime with Zod where a boundary demands it (McDonald, 2024; OpenAPI Initiative, 2021). The generated file is committed, and regenerating it after a route or schema change is a standing rule. The effect is that a backend schema change that the frontend has not absorbed fails at compile time rather than at run time.

## Infrastructure and Deployment Modes

The stack is described once, in `docker-compose.yml`, and specialised by overlays (Docker Inc., 2024). This is the single most frequently misunderstood point about the deployment, so it is stated directly: **the four running modes are layered configurations of one composition, not four different tools.**

The base composition defines four services: `keycloak-db`, `keycloak`, `api` and `web`. It builds production images, runs them detached and publishes ports 3000, 8000 and 8080 on the host. This is what `make up` runs, and it is the closest thing to production that works on a laptop.

The **development overlay** (`compose.dev.yml`, invoked by `make up-dev`) mounts the source tree into the containers and replaces the entrypoints with `uvicorn --reload` and `next dev`. Everything else is inherited.

The **production overlay** (`docker-compose.prod.yml`) adds a Caddy `proxy` service that terminates TLS on port 443 and routes by path, repoints the public URLs at a single origin, and withdraws the published application ports so that nothing but the proxy is reachable. §7.4 documents the resulting deployment as a runbook.

Outside Docker entirely, `make dev` runs the API and web dev servers directly on the host. This is the fastest inner loop and the one module authors are directed to (§8.1), at the cost of requiring `uv` and `pnpm` locally.

One further service exists but is off by default. A Neo4j container is declared under the `graph` compose profile and is started only when a module needs a graph database beside the platform (§5.5). This is the sanctioned pattern for modules that require a whole server rather than a library, and keeping it behind a profile means the default installation does not pay for it.

## Authentication, Authorisation, and Administration

Login is mandatory; there is no anonymous mode and no path that reaches data without an authenticated identity.

The identity chain has four links. The browser is redirected to the bundled **Keycloak** realm, which either presents its own login form or delegates to the university's identity provider. Keycloak returns an authorisation code to the web application, where **Auth.js v5** exchanges it and issues a session (Auth.js, 2024). Those sessions are **JWT-only**: there is no database adapter and no session table on the application side, and token rotation happens inside the `jwt` callback. The browser then calls the API with a bearer token, and the API validates it with **PyJWT against the realm's published JWKS endpoint**, caching the key set so that validation costs no network round trip. The `sub` claim of the validated token is the user identity for everything that follows, and the first time a `sub` is seen the API upserts a row for it.

Authorisation uses exactly one primitive: the realm role `admin`. There are no per-resource permissions, no groups mapped to capabilities and no policy language. This is a deliberate simplification for a system in which almost all authorisation questions are answered by ownership rather than by role: a user may act on a resource because it is theirs, which §4.5 enforces structurally. The role is needed only for the small set of actions that are inherently cross-user.

The administrative surface consists of an overview of system and usage state, live control of worker concurrency, module policy (an administrator can pin a module as globally enabled or locked), user and team administration, and a **consistent metadata export**. The export produces a single SQLite file containing a transactionally consistent snapshot of the entire metadata database and is gated on the `admin` role. Its governance implication is stated here rather than buried: **the exported artefact contains every user's accounts, usage data, process metadata and settings**, so the download is itself sensitive and the role that unlocks it should be assigned as sparingly as any other administrative credential.

Usage capture deserves the same directness. The platform records interaction events locally, and the data model follows the reference data model for process-related user interaction logs of Abb and Rehse (2024): interaction events are stored with OCEL-shaped objects (UI element, UI group, application, system, user, task) and the object-to-object and event-to-object relations between them, so that the platform's own usage is itself analysable as an object-centric event log. Nothing is transmitted off the host. The default policy, however, is `force`, which enables capture for every user and hides both the onboarding privacy step and the privacy settings tab; the operator can set the policy to opt-out or opt-in instead. §7.6 returns to this as a governance decision rather than a configuration detail.

## Tenant Isolation as a Cross-Cutting Invariant

Isolation in Mate is not a feature with an owner; it is a property that every layer must independently maintain. It is stated here in the form a future contributor has to keep true.

> **Invariant.** Every artefact that belongs to a user is keyed by that user's Keycloak `sub` claim, at rest and in flight. A component that produces a user-scoped artefact without that key is broken, whether or not anything currently reads it.

The claim is honoured in four places. **Database rows**: every user-scoped table carries a `user_id` column that references the users table with cascade deletion, and access goes through ownership helpers rather than through ad-hoc filters, so that "did this query forget the tenant predicate" is a question about a handful of functions rather than about every route. **On-disk artefacts**: Parquet event data and module result caches live under `data/users/{user_id}/`, so the filesystem path itself encodes the boundary. **Job records**: a job row carries its owner, and the job runtime's pause and resume operate per user, so one tenant pausing their queue does not stall another's. **Live events**: every user-scoped bus envelope carries `user_id` as a reserved key, and the SSE fan-out filters server-side on it before writing anything to a connection.

The last of these is the one with the sharpest failure mode. The event bus is an in-process publish/subscribe channel with no notion of tenancy of its own; isolation is enforced at the point of fan-out by comparing the envelope's `user_id` with the connected user's. An event emitted **without** a `user_id` is therefore not filtered out and reaches every connected session. This is the correct behaviour for genuinely global events such as a platform-wide notice, and it is a data leak for anything else. The rule for contributors is accordingly absolute: **a user-scoped event that omits `user_id` leaks to all users**, and the omission is silent, because nothing crashes and nothing logs a warning. §8.11 lists it among the failure modes an author must know.

One exception is deliberate and confined. A dashboard may be shared, which grants named recipients **read** access to that dashboard and, transitively, to the underlying log's data as rendered by the dashboard's cards. All predicates that widen access this way live in a single module, so that the surface capable of crossing an account boundary is small enough to audit in one sitting. Recipients cannot mutate the dashboard or reach the log by any other route.

## Data Management: Ingest, Columnar Storage, and Offloading

An upload is staged to disk, its format is detected, and an import job is enqueued; the request returns a log identifier and a job identifier immediately. The import job parses the source, writes the canonical form, and moves the log's status forward. Parsing dispatches on format: XES and its gzipped variant through a streaming XML reader, CSV through a column-mapping step that the user completes in the import wizard, generic XML through a mapping-based path for advanced users, and OCEL 2.0 in its JSON, XML and SQLite encodings through a separate object-centric path.

The canonical form is written once, per log, as a small directory:

```
data/users/{user_id}/event_logs/{log_id}/
  meta.json          source format, ingest statistics, detected schema, mapping
  events.parquet     flat event table, sorted by (case_id, timestamp)
  cases.parquet      cached case-level aggregates
  original.{ext}     the untouched upload, for audit and re-export
  ocel/              written only for object-centric imports
    events.parquet  objects.parquet  relations.parquet  o2o.parquet
```

The rationale is the structural assumption of §2.1. XES on disk is XML, and answering "how many events per activity" from it means parsing hundreds of megabytes of markup for a single aggregation. Normalising once into a columnar format makes that aggregation essentially free, shrinks the data by roughly an order of magnitude, and is read natively by every library a module might want to use. Keeping the original upload beside the derived form preserves auditability and makes re-import possible without asking the user for the file again.

Analytical queries therefore run against DuckDB reading those Parquet files, while metadata stays relational in SQLite. DuckDB can attach the SQLite database, so a query can join event data against process metadata in one statement without an export step. Because a DuckDB connection is single-threaded, connections are pooled per worker thread through context variables rather than shared, and the pool re-attaches the metadata database on demand. Query-level resource limits (thread count and memory ceiling) are configurable, so that one large query or one dashboard full of cards cannot claim every core and all memory on a shared machine.

Beyond a certain data volume a single VM's disk becomes the binding constraint, and the platform therefore supports an **object-storage backend**. The first implementation was a write-through mirror, and it is worth reporting that it did not work, because the reason is instructive. A mirror writes locally and then uploads; on a read miss it pulls the whole directory back and marks it hydrated. The local copy was never evicted, so enabling object storage added a second copy and an upload cost without shrinking the VM at all. Worse, the artefacts that actually consumed the disk bypassed the mirror entirely: the SQLite metadata database, which grows unboundedly with job and usage rows, each module's virtual environment at anywhere from a hundred megabytes to two gigabytes, the cached Python runtimes, and uploaded module packages. Hydration was also whole-tree and per-process, so a cold read of a ten-gigabyte log pulled all ten gigabytes before DuckDB touched a row, once per worker.

The redesign inverts the relationship. **Object storage is authoritative; local disk is an LRU cache** bounded by an explicit byte budget, with age-guarded eviction and a dry-run mode for a soak period before deletes are enabled. The bypass holes were closed so that the large artefacts participate. Migration between backends moves existing data rather than stranding it, and the previously declared per-user quota is now enforced. Hydration was made partial and shared rather than whole-tree and per-process. With a budget configured, the VM's local footprint is bounded by the active working set plus module runtime artefacts, rather than by total data ever imported.

Two seams are deliberately left open for multi-node operation and are named again in §11.4: the cache is per-node with no cross-node coordination, and the metadata database remains a single-writer store and therefore a single point of failure whose loss would orphan every object in the bucket.

## Backend: API Surface, Job Runtime, and Event Bus

**The HTTP surface.** All routes live under `/api/v1/`, organised by resource: event logs and their data, folders, datasets, jobs, modules, dashboards, sharing, teams, watched folders, preferences, onboarding, API tokens, the assistant, usage, and an administrative group covering users, teams, jobs, modules, policies and insights. Module-defined routes are mounted under `/api/v1/modules/{module_id}/...`, so a module's surface is namespaced by construction and cannot collide with the platform's or with another module's. OpenAPI is generated rather than written, and the frontend's types are generated from it in turn, so there are no hand-written API types anywhere in the repository.

**The job runtime.** Every operation that can outlast a request is a job. A producer inserts a row into the SQLite jobs table, assigns it a time-ordered UUID v7 identifier and pushes a marker onto an in-process `asyncio.Queue`; a pool of asyncio worker tasks consumes it. Concurrency defaults to two and is changeable live by an administrator, which resizes the pool without interrupting running work. Cancellation is cooperative, through a per-job event that handlers check. Retry re-enqueues the same payload under a fresh identifier, so the failed attempt remains in the record. Because job state is in SQLite rather than in memory, a restart does not lose the queue: on boot the runtime reconciles what it finds. There is no Redis, no Celery and no broker, which keeps the deployment at two application containers. For genuinely CPU-bound work that would otherwise hold the event loop, a process pool is available to module authors through the context, with the pool sized to the worker concurrency and a per-job execution timeout that can kill a runaway offload rather than merely marking a database row.

**The event bus.** State changes are distributed through an in-process publish/subscribe bus. Publishers emit an envelope of topic, payload and timestamp; subscribers register topic patterns and are each fed through their own bounded queue. The queue policy is the design decision worth explaining. Each subscriber's queue holds a fixed number of envelopes, and when it is full **the oldest envelope is dropped** rather than the publisher blocking. This is correct because of what the bus actually carries. A `job.progress` tick is one sample of a continuously updating quantity; losing it costs the user a slightly staler progress bar until the next tick arrives a moment later, and the alternative, letting one slow browser connection stall the import that is producing the ticks, is far worse. A terminal event such as `job.completed` is not expendable in the same way, since dropping it would leave the interface believing a finished job is still running. The bus does not distinguish the two, so the property is achieved differently: terminal state is persisted to the jobs table before it is published, and the frontend reconciles against that table on reconnect. The bus is treated as a low-latency accelerator over authoritative database state, never as the source of truth.

Both live streams the browser consumes are bus subscribers: the session-wide `GET /api/v1/events`, filtered by topic, and the per-job `GET /api/v1/jobs/{job_id}/stream` for the focused job's high-frequency progress. Both are Server-Sent Events, for reasons documented in §4.10.

## Progress Reporting and Readiness Semantics

A freshly imported log is not immediately useful. Several modules precompute results on import, and opening the log before they finish would show a page of empty cards. The platform therefore holds a log in a `processing` state until the analyses it is waiting for are done, and the semantics of that gate are the subtlest part of the runtime.

A log moves through `importing` while its source file is being parsed, then `processing` while modules precompute against it, then `ready`, or `failed` if the import itself errored. The set of modules that must finish, the **expected set**, is computed once, at import time, and frozen. Computing it lazily would introduce a race in which the coordinator observes zero subscribers before any has registered and flips the log to `ready` immediately.

The expected set is not simply the modules that subscribe to the import event. It is the **transitive precompute closure**: starting from the job-backed subscribers to `log.imported` or `ocel.imported` that the importing user actually has installed, the loader walks the graph of declared `provides` and `consumes` topics, pulling in every module that subscribes to a topic another expected module emits. Ordering between modules is therefore expressed as an **event subscription, not a priority number**. A module that must run after discovery subscribes to `discovery.completed`, and the platform emits that event automatically when a module's precompute job succeeds. §5.6 explains why this is the better of the two designs.

Three properties follow. Because the closure is built from the actual subscription graph, a `consumes` entry naming a topic that no loaded module emits is simply never reached, so a stale declaration degrades to a no-op rather than to a stuck log. Because a failed or cancelled module emits no completion event, its dependants are **cascade-skipped** rather than stranded waiting forever. And because the gate releases on any terminal status, `completed`, `failed` or `cancelled`, a module that crashes delays a log by the duration of its own failure and no longer.

Completion is derived from the job rows themselves, linked to the import job by a parent reference, rather than from an in-memory counter, so an API restart mid-precompute recovers the correct state by re-deriving it from the database. The import job's payload also carries the computed plan, which the interface renders as a checklist of what is waiting, what has finished and what was skipped.

Progress reporting inside a job is **optional and never enforced**. A handler may report a fraction, an absolute current-and-total pair which additionally enables an estimated time remaining, or a plain running counter for work whose scope is unknown. A job that reports nothing is not an error: it degrades to an indeterminate progress bar, and if it stops reporting for about three minutes the interface adds a client-side hint that no progress has been seen recently. Making progress a runtime requirement was considered and rejected, because the enforcement would have to be a timeout, and a timeout that kills a legitimately slow computation is a worse failure than a bar that does not move. Emitting progress from a long job is therefore a guideline and an item on the author checklist rather than a gate.

## Frontend: Structure, State, and Interaction Model

The application is organised by route group. An authentication group holds the login flow; the platform group holds everything behind the session: processes and their detail pages, the module pages beneath each process, dashboards, settings, the administrative area, and the user profile.

Data access is split by where it runs. Server components fetch through a server-side wrapper that reads the cookie-backed token, which serves the initial render. Everything interactive goes through the browser wrapper, which attaches the bearer token and is consumed by TanStack Query hooks. The division of labour between the two state systems is deliberate: **anything that came from the server lives in the query cache, and only genuinely local interface state lives in Zustand**. Preferences that look local, such as theme, density and visualisation settings, are held in Zustand for instant reads but are bridged to per-user server state, so that they follow the account across browsers instead of bleeding between accounts through shared browser storage. The same rule applies to onboarding completion and similar account-scoped flags: they are server state, not browser state.

Three interaction conventions follow from the product principles and are applied consistently.

**Optimistic mutation with snapshot rollback for edits.** A mutation that modifies an existing resource cancels in-flight queries for it, snapshots the cache, and writes the expected next state immediately; on error it restores the snapshot; on settle it invalidates so the server reconciles. Creation and duplication use plain invalidation instead, because there is no prior row to roll back to. The distinction is enforced by convention and by review rather than by the type system.

**Skeletons rather than blocking spinners.** Above-the-fold content renders placeholder shapes matching the eventual layout while it loads. Spinners appear only inside buttons during submission. The intent is that the page's structure is legible before its content arrives.

**Motion as state feedback only.** Transitions are short and are used to communicate that something changed, never as decoration, and `prefers-reduced-motion` is honoured throughout.

Module-contributed panels are the one part of the frontend that is not built by the Next.js build. A separate script bundles each module's declared panel and widgets with esbuild into the module's own output directory, running once at container start in production and in watch mode during development. Every shared dependency, React itself, the query client, the component primitives, the charting and graph libraries, is marked external and resolved at run time from a shared runtime object that the host installs lazily. This is what allows a panel to use the host's React instance, so that hooks and context work across the boundary and a panel inherits the host's theme automatically. The cost is a constraint on authors: a panel may import only from an explicit allow-list of platform paths. That list is a single file read by both the bundler and the runtime installer, and a parity test asserts the two never diverge. §5.7 develops the reasoning, and §8.7 states the symptom when the constraint is ignored.

## Error Handling and Operational Robustness

The mechanisms in this section were not planned. Each is a response to a defect that was observed in operation, and they are collected here because scattering them across the sections they touch would hide the pattern.

**The transport that the proxy chain would not carry.** Live updates were originally WebSockets. They worked locally and failed silently in production. The cause is in the proxy chain: the university's edge proxy forwards HTTP to the VM but does not carry WebSocket upgrades, so the handshake arrived at the API as a plain `GET` with the upgrade headers stripped and returned 404. Nothing crashed; job progress simply never updated, and only in production. The response was to migrate both live streams to **Server-Sent Events over `fetch`**, which ride exactly the path the assistant's token streaming already used successfully. Two secondary benefits fell out of the change. Because `fetch` can set headers, authentication moved from a token in the query string to an `Authorization` header, so tokens stopped appearing in the API's access logs. And because SSE is HTTP, a 401 is unambiguous and means "sign in again" rather than triggering an endless reconnect loop. Both streams reconnect with exponential backoff capped at eight seconds. The client file is still named `ws.ts`, because `@/lib/ws` is a published module-SDK import alias and renaming it would break third-party panels; the header comment explains why.

**Worker crashes.** A bridged module runs in a separate process, and separate processes die. The host supervises its worker and respawns it with exponential backoff, up to a bounded number of attempts with a capped delay, rather than letting one module's crash disable it until the next platform restart. The behaviour is covered by a regression test. A related hazard is the reverse direction: a worker whose parent has died must not survive as an orphan holding a socket and a virtual environment, so the protocol requires every worker to implement a parent-death guard, and that too has a test.

**A message-size limit that killed workers.** The bridge frames messages as newline-delimited JSON read through asyncio's stream reader, whose default line limit is 64 KiB. Handler return values, cache writes and query result sets routinely exceed that, and a single oversized line raised an internal buffer error that tore down the connection and took the worker with it. The limit is now raised well beyond any plausible metadata payload, and, more importantly, bulk data no longer travels the socket at all: DataFrames cross the boundary as a Parquet file on the shared filesystem, so the socket carries only control messages and small results.

**Dependency installation failures at load time.** Each module resolves its own dependencies at startup, and resolution can fail: a bad version specifier, an unreachable index, a package with no wheel for the platform. A failure here is contained to the module. It is reported with the resolver's own error text, the module is marked as failed to load, and the rest of the platform starts normally. A related lesson concerned the installer itself: the original implementation used `uv sync`, which writes a lock file, and lock-file writes fail on macOS Docker Desktop bind mounts because of the file system layer's restrictions on atomic renames. Switching to `uv venv` plus `uv pip install`, which writes no lock file, made the same code path work on every developer machine.

**Degradation when a stream stalls.** If a live stream drops, the interface does not freeze and does not silently lie. Jobs reconcile against the jobs table on reconnect, and a running job that has reported no progress for about three minutes is annotated as such rather than left animating. The intent throughout is that the failure of a convenience layer degrades the experience without corrupting the state.

## Machine Access: MCP Server and Integrated Assistant

Two access paths exist that are not the graphical interface, and both are defined primarily by where their data boundary sits.

**The MCP server** exposes the platform to external AI clients over the Model Context Protocol. It is off by default and enabled by configuration. Eight toolsets are available, covering metadata, processes, analysis, dashboards, jobs, watched folders, account settings and administration, with the administrative set excluded unless explicitly listed. Three properties define its security posture. First, **the caller's identity is never a tool argument**: it is resolved from the authenticated principal on the connection, so a token can only ever act as its owner and the tenant invariant of §4.5 holds by construction rather than by validation. Second, there is a **data wall**: raw event rows are never returned. Reads are aggregates and curated module outputs, so an external client can ask what the process looks like but cannot exfiltrate the log row by row. Third, the server is scope-gated, rate-limited per minute with a burst allowance, concurrency-capped per user and globally, and can be placed in a read-only mode that either unregisters the write tools at boot or makes them refuse at run time. Authentication is by personal access token or by OAuth 2.1 through the same Keycloak realm, and browser-based clients are additionally guarded against DNS rebinding by an origin check. The tool catalogue itself is reference material and lives in the appendices.

**The integrated assistant** ("Mate AI") is a chat panel inside the application. Rather than coupling the platform to a particular model vendor, it targets any OpenAI-compatible endpoint: the user supplies their own base URL, API key and model name, and may customise the system prompt. Those credentials are stored in the local metadata database as a per-user setting and are never transmitted anywhere except to the endpoint the user configured. The assistant is context-aware, able to reference the active log, recent job outcomes and the set of enabled modules, and it can carry out platform actions on the user's behalf through the same guarded surface the MCP tools use.

The data boundary is the point to be clear about, because the two paths differ. The MCP server moves data **outward** from the platform to a client the user has authorised, under a token the user issued, restricted by scope and by the data wall. The assistant moves data **outward to a third-party model provider** that the user chose, and the platform cannot constrain what that provider does with it. In both cases the platform's position is the same: the boundary is explicit, the credential is the user's, and nothing leaves the host unless the user configured a destination. One bundled module makes the same trade-off internally and is flagged for it in its own description, because a module that calls an external model is a module that sends the user's data off the machine (§6.5).
