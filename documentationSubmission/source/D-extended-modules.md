# Extended Module Descriptions

Per module: the algorithmic background, the parameters a user sets, what the output means, and known limitations. §6.2 gives the short form and the size table.

**Discovery** (`foundation`, in-process) wraps PM4Py's discovery algorithms. The Alpha miner derives footprint relations between activities and lays maximal causal activity sets down as places (van der Aalst et al., 2004); the Inductive miner recursively splits the directly-follows graph into a sound process tree, convertible to a Petri net and to BPMN; the heuristics miner suppresses infrequent behaviour by threshold before inferring dependencies. *Parameters:* algorithm, noise threshold, activity and path frequency filters, layout mode. *Output:* a DFG with frequency or duration annotations, a Petri net, a process tree, a heuristics net and a BPMN diagram, with a layout following the backbone-based process map approach of Lee et al. (2026). *Limitations:* the layout degrades on graphs with many activities, which §11.6 proposes replacing; the DFG cannot distinguish concurrency from interleaving; Alpha is sensitive to noise and is retained mainly for teaching and comparison.

**Performance** (`foundation`, in-process) computes throughput, lead and cycle time, sojourn and waiting time, the 90th-percentile cycle time, and a performance-annotated DFG. *Parameters:* time unit, percentile, aggregation. *Limitations:* waiting and sojourn time separate only when events carry both a start and an end timestamp; without discovery installed, metrics are computed against raw activity labels.

**Object-Centric Discovery** (`foundation`, in-process) discovers a process from OCEL logs (Berti et al., 2023; van der Aalst, 2019), producing object types and counts, the object-centric DFG, an object-centric Petri net, an activity-to-object-type map and an object relationship graph. *Limitations:* offered only for object-centric logs; OC-DFGs become dense quickly on logs with many object types.

**Conformance Checking** (in-process) performs token-based replay by default and alignments optionally (Carmona et al., 2022; Rozinat & van der Aalst, 2008). *Parameters:* the uploaded BPMN model, the technique, activity-name matching. *Output:* fitness, precision, per-activity deviations, and the model painted with them. *Limitations:* alignments are considerably more expensive than replay and can dominate the job's runtime; results depend on how well activity names in model and log match.

**Complexity** (in-process) computes entropy-based complexity over variants and activity sequences, plus Lempel-Ziv complexity, affinity, structure and Pentland's task and process complexity, following Augusto et al. (2022). *Limitations:* metrics are not comparable across logs of very different size without normalisation. **Complexity V2** (in-process) implements the 28-metric suite of Langer (2025), spanning entropy, size, variation and trace-distance families including edit distance and structural variety, plus the directly-follows transition-probability matrix. *Limitations:* some distance metrics are quadratic in the number of variants and become expensive on highly variable logs.

**Complexity Over Time**, **Complexity V2 Over Time** and **Performance Over Time** (in-process) slice the log into time windows and score each with the corresponding suite. *Parameters:* window size and overlap. *Limitations:* windows with few cases produce unstable values; the three duplicate their windowing logic (§11.3).

**Log Evolution** (in-process) is descriptive rather than algorithmic: case arrivals against completions, work in progress over time, the changing activity mix, and a dotted chart of every event. *Limitations:* the dotted chart is sampled above a size threshold.

**CV4CDD** (in-process) encodes the log as an image representing behavioural similarity over time and runs a trained object-detection model over it to locate drifts and classify them as sudden, gradual, incremental or recurring (Kraus & van der Aa, 2024, 2025). *Parameters:* the model path or the globally pinned model, window size, detection threshold. *Limitations:* requires a trained model, which is not shipped, so without one every import starts a job that fails (§11.3); accuracy depends on the log resembling the training distribution.

**Concept Drift Explainer** (in-process) takes CV4CDD's drift points, retrieves passages from user-uploaded enterprise documents through a vector store, and asks a hosted language model to rank candidate causes with citations (Schaffner, 2025). *Parameters:* provider credentials, model, index, retrieval depth. *Limitations:* **transmits data to an external provider** and declares itself not confidentiality-safe; explanations are only as good as the uploaded corpus; the hard dependency on CV4CDD means it is cascade-skipped when drift detection fails.

**AgentSimulator** (subprocess) learns each resource's behaviour, working calendars and handover patterns from the log, simulates the process as interacting agents, and generates synthetic logs scored against a held-out slice (Kirchdorfer et al., 2025). *Parameters:* train and test split, number of simulations, agent discovery mode. *Limitations:* runs on its own interpreter with twelve exactly pinned dependencies; the longest-running module in the set.

**Actor Performance** (subprocess, sidecar) builds an event knowledge graph and decomposes waiting time between process steps by actor behaviour, distinguishing direct continuation, continuation after interruption, and handover to an actor who was idle or busy (Klijn et al., 2024). *Limitations:* requires the graph-database sidecar, without which the module shows a setup screen; it declares no import subscription, so an installation without the sidecar produces no failed jobs.

**Alpha Miner (Java)** (JVM runtime) implements the classic Alpha algorithm in Java and ships as a fat jar (van der Aalst et al., 2004), exposing the Petri net as a typed dataset rendered by the platform's generic graph visualisation. *Limitations:* analytically redundant with Discovery; it exists as the reference implementation of the polyglot runtime.

**Process Comparison** (in-process) compares two filtered views: an overlaid DFG diff, variant differences, similarity by earth mover's distance and footprints, and per-activity frequency changes. *Limitations:* the diff is hard to read when the two views share few activities.

**Pcomp** (in-process) tests whether two logs differ in a statistically meaningful way, using earth mover's distance with a permutation or bootstrap test (Pitsch et al., 2025). *Parameters:* test type, number of resamples, distance dimension. *Limitations:* resampling is expensive on large logs, and a p-value answers whether a difference exists, not whether it matters.
