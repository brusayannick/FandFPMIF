# Conceptual Foundations

## Process Mining: Terminology and Data Basis

Process mining is a discipline situated between data science and process science that analyses event data in order to discover, monitor and improve real processes (van der Aalst, 2016). Rather than relying on how a process is assumed to run, it derives knowledge from the digital traces that process executions leave behind in an organisation's information systems, and so complements the predominantly model-driven perspective of classical business process management (van der Aalst et al., 2012).

The starting point for every process mining technique is the **event log**. An event log is a collection of **cases**, each case being a **trace**: a sequence of **events** ordered in time. An event minimally records a **case identifier**, an **activity** label and a **timestamp**, and is frequently enriched with further attributes such as the executing **resource** or a completion timestamp (Reinkemeyer, 2020b). Traces that consist of the same activity sequence form a **variant**, and the distribution of variants is often the first thing an analyst looks at, because it separates the dominant execution paths from the long tail of exceptions.

The **XES** standard (IEEE Standards Association, 2016) gives this structure an interchange format. An XES file is XML with a fixed hierarchy of log, trace and event elements, and an extension mechanism that assigns semantics to attribute keys, so that a reader knows which attribute is the timestamp and which is the activity. Tabular **CSV** input carries the same information without the semantics: the columns exist, but which column is the case identifier is not recorded anywhere in the file and must be supplied at import. This is not a superficial difference. It is the reason the platform's CSV path needs a column-mapping step and the XES path does not (§4.6).

A more recent development, **object-centric process mining**, relaxes the assumption that each event belongs to exactly one case (van der Aalst, 2019). In many real processes several object types interact, an order relates to several items and an item to several deliveries, and forcing such data into a single case notion produces the well-known distortions of convergence and divergence. The **OCEL** standard (Ghahfarokhi et al., 2021) represents these logs as events, objects and the relations between them rather than as case-attributed traces.

One structural assumption underlies everything that follows. An event log is an **ordered, case-attributed sequence of recorded events, written once and then read many times**, and the overwhelming majority of reads are aggregations over a small number of columns across a large number of rows. Every later decision about how the platform stores and queries logs is a consequence of that observation, and §4.6 makes the derivation explicit.

## The Analytical Disciplines

The literature distinguishes three principal types of analysis over an event log (van der Aalst, 2016; van der Aalst et al., 2012).

**Process discovery** derives a process model from an event log without any a priori model. It consumes a log and produces a model. Since several models can explain the same log, the quality of a discovered model is weighed along four competing dimensions: **fitness** (does the model permit the behaviour in the log), **precision** (does it permit little else), **generalisation** (does it permit plausible unseen behaviour) and **simplicity** (is it readable). These dimensions trade off against one another, which is why a platform must be able to offer several discovery algorithms rather than a single canonical one.

**Conformance checking** compares a model with a log to detect and quantify deviations between intended and observed behaviour (Rozinat & van der Aalst, 2008). It consumes a log *and* a model, and produces a diagnosis: fitness and precision scores, and a localisation of where the two disagree. Modern treatments distinguish replay-based from alignment-based techniques, the latter being more informative and considerably more expensive (Carmona et al., 2022).

**Enhancement** repairs or extends an existing model using the log, for example by projecting performance information such as bottlenecks onto it. It consumes a log and a model and produces an enriched model.

Read as a set, these three have a shared shape that matters architecturally. Each consumes an event log, optionally consumes an artefact produced by another technique, and produces an artefact of its own. None of them needs to know where the log came from, who owns it, or how the result will be displayed. This is what licenses the platform's central abstraction, **log in, artefact out**, and it is why that abstraction can be expressed as a single uniform module contract rather than as three different plug-in types (§5.2).

Two further concerns recur throughout this report because they motivate several of the bundled modules. **Concept drift** is the situation in which a process changes while it is being analysed (Bose et al., 2014). It undermines methods that assume a stable underlying process, because two iterations of a process analysed as one log yield a model that describes neither. The literature distinguishes four drift types, sudden, gradual, incremental and recurring, and three analytical tasks: change point detection, change localisation and characterisation, and change process discovery. Surveys agree that no single detection method dominates on accuracy, latency, robustness and scalability simultaneously (Adams et al., 2023; Elkhawaga et al., 2020; Sato et al., 2022), which is itself an argument for a platform on which several can be installed side by side. **Process complexity** describes the degree to which a process is difficult to understand, analyse or explain. Traditional measures are structural, computed over a process model, and therefore describe the intended design rather than the observed execution; behavioural measures computed directly from the event log capture what actually happened, and correlate with the quality of the models that discovery algorithms produce from that log (Augusto et al., 2022; Langer, 2025).

## Model Notations and Performance Measures

The platform renders discovered models in five notations, and the reader needs only enough of each to interpret the screenshots and module descriptions later; formal semantics are out of scope.

A **directly-follows graph** (DFG) has one node per activity and an edge from *a* to *b* whenever *b* was observed directly after *a*, usually annotated with the frequency or the mean duration of that transition. It is the most immediately readable representation and the least expressive: it cannot distinguish concurrency from interleaving. A **Petri net** consists of places and transitions and does express concurrency, choice and synchronisation precisely; the Alpha and Inductive miners produce Petri nets. A **process tree** is a hierarchical representation in which operators such as sequence, exclusive choice, parallel and loop compose sub-trees; it is sound by construction, which is why the Inductive miner produces one internally. A **heuristics net** sits between the DFG and the Petri net, using frequency thresholds to suppress infrequent behaviour before inferring dependencies. **BPMN** is the notation practitioners actually model in, and the platform converts discovered models into it so that a discovered process can be compared with a documented one.

The time-based measures used throughout are equally few. **Throughput** is the number of cases completed per unit of time. **Lead time** (also cycle time) is the elapsed wall-clock time from the first to the last event of a case. **Sojourn time** is the time an individual activity occupies, and **waiting time** the interval between the completion of one activity and the start of the next; separating the two requires a start and an end timestamp per event, which is why several modules declare `end_timestamp` as an optional column that unlocks additional output. Because these distributions are heavily right-skewed, **percentiles** rather than means are the honest summary, and the platform reports the 90th percentile alongside the mean throughout.

## Platforms versus Libraries: A Conceptual Distinction

Chapter 3 compares products of very different kinds: a cloud suite sold to enterprises, a desktop research framework, and a Python package. Comparing them at all requires a criterion that says what they have in common and where they differ, and the distinction between a library and a platform supplies it.

A process mining **library** provides algorithms. It exposes functions that take data structures and return data structures, and it makes no claim about where the data came from, who is allowed to see it, or what happens when the function takes ten minutes. PM4Py is the canonical example (Berti et al., 2023): it is an excellent implementation of a large body of techniques and, by design, nothing else.

A process mining **platform** provides algorithms *and* everything that makes running them repeatedly, by several people, over time, tractable. Concretely, it adds five things a library does not have:

- **Persistence.** Data and results survive the session. A log imported today is analysable tomorrow without re-import.
- **Identity.** There is a notion of *who* is asking, and the answer differs by asker.
- **Concurrency.** Several analyses, and several people, proceed at once without interfering.
- **An interface.** Results are presented to somebody who is not the person who wrote the algorithm.
- **A lifecycle for third-party extensions.** New capability can be added, configured, updated and removed by someone other than the original authors, while the system is in use.

These five properties are used as the evaluation grid in Chapter 3, alongside criteria that are specific to the setting of this project (deployment locality, licensing, analytical coverage). The distinction is operational rather than definitional: it does not say that libraries are inferior, but it does say that the work of turning a library into something an analyst can use is real work, and that measuring a tool against criteria it never intended to satisfy would be a category error. Chapter 3 accordingly reports what each tool is *for* before reporting how it scores.

The distinction also frames this project's own contribution precisely. Mate implements very few process mining algorithms itself; almost all of its analytical capability comes from PM4Py and from the reference implementations published alongside research papers. What it contributes is the platform layer, and specifically the fifth property, the extension lifecycle, which is the one the existing tools treat least seriously.
